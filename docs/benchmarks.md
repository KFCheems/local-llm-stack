# 实测数据（RX 7900 XT 20GB / 9800X3D / 32GB RAM / llama.cpp Vulkan b11212）

以下全部为本机实测，非推测。供同类硬件做容量规划参考。

## 1. 上下文容量与速度悬崖（27B 稠密 IQ4_XS，权重 14.3GB）

KV 每 token 占用（GPU 显存差值法实测）：

| KV 量化 | 每 token | 32K 全套 VRAM |
|---|---|---|
| q8_0 | ~36 KB | 15.9 GB |
| q4_0 | ~19.5 KB | 15.8 GB |

实测曲线（q4_0 KV，-fa on，300 token 生成，经门卫全链路；多次复测）：

| 上下文 | VRAM | 解码速度 | KV 溢出到共享内存 |
|---|---|---|---|
| 32K | ~16.6 GB | 35.2 tok/s | 无 |
| 64K | ~17.4 GB | 35.2 tok/s | 无 |
| **96K** | ~18.1 GB | **35.3 tok/s** | **无 ← 定档** |
| 128K | 18.7 GB | 19.1 tok/s ❌ | 0.74 GB |
| 160K | 18.7 GB | 19-22 tok/s ❌ | 1.64 GB |

**结论（2026-10-05 修正版，替代早先"176K 算子悬崖"的说法）**：
真正机制是 **WDDM 显存溢出** —— 160K/128K 时 KV 分配几乎吃满 20GB，
Windows 把 0.7-1.6GB KV 页挤到共享内存（走 PCIe 的系统 RAM），
每个 decode 步的带宽被腰斩。96K 是"KV 完全驻留显存"的最大档位，
**全速 35.3 tok/s + 3 倍于 32K 的窗口**。边界会随桌面占用漂移
（曾测到过 128K/160K 短暂全速，不可靠），重启后重测也会变化。

**结论**：176K 处存在算子分档悬崖（不是显存不足——176K 与 160K 显存相同），
Vulkan 后端注意力内核在该 KV 规模切换到慢速路径。20GB 卡 + 27B 稠密的
最优点就是 **160K**。算账公式：
`VRAM ≈ 权重 + 1.8GB 运行时 + 上下文 × 每token KV`，但**必须实测档位**。

（旁证：35B-A3B MoE 在同卡标称 256K 上下文，但其前端的压缩代理实际只让
有效上下文用到 32K —— 标称窗口 ≠ 可用窗口。）

## 2. 投机解码 A/B（27B 稠密，全 GPU）

| 方案 | 解码速度 | 备注 |
|---|---|---|
| 基线 | ~35 tok/s | |
| MTP 官方草稿（1.37GB，接受率 ~50%） | **9.7 tok/s** ❌ | 验证批次吃掉带宽收益 |
| ngram 投机（零成本） | ~37 tok/s | 一般文本无增益 |

MTP 投机适合"权重在内存/磁盘调页"的 MoE 场景（实测在调页型 131B 上是
3.9 tok/s，更糟）；全 GPU 稠密模型上结论一致：**别开**。

## 3. 子代理"手"选型横向对比

两个候选（同为稠密 27B、同卡、同参数 max_output_tokens=2000、同链路），
6 项子代理典型任务：

| 任务 | 候选 A（Cyber 特化） | 候选 B（官方 27B 去审查） |
|---|---|---|
| T1 代码生成（均衡切分） | **FAIL**：思考失控烧满 2000 token，正文截断 | PASS，一发完整正确 |
| T2 代码修改（去重 bug） | PASS（1024 tok） | PASS（**283 tok，省 3.6 倍**）|
| T3 工具调用 | PASS | PASS |
| T4 指令遵循（逐字输出） | PASS | PASS |
| T5 中文理解 | PASS | PASS |
| T6 综合重构（列表推导） | PASS | PASS |

**结论**：速度相同（同为带宽极限），可靠性和思考开销才是子代理选型的决定因素。
选"手"时优先测 T1（生成可靠性）和 T2 的 token 效率。

## 3.5 链路逐跳延迟与调参实测（2026-10-05）

80 token 流式生成（27B 稠密 IQ4_XS，160K 档，热引擎）：

| 路径 | TTFB | 总耗时 |
|---|---|---|
| 直连引擎 :8093 | 0.02-0.16s | 2.17-2.36s |
| 经门卫 :8092 | 0.13-0.16s | 2.32-2.46s |
| 经 shim :8088 | **1-2ms**（响应头立即回） | 2.35-2.50s |
| 公网 api.qqking.top | 1.2-2.6s | 3.7-5.4s |

- 本地代理链（shim+门卫）总开销 ≈ 50-300ms，占短响应 5-8%，**不是瓶颈**
- 公网 TTFB ~1.4s = 大陆到 CF 边缘的结构性距离（已 http2/0-RTT 优化过）
- TCP_NODELAY 已加到 shim 与门卫的全部套接字（SSE 是 token 级小写入，防 Nagle 合包）
- llama-bench 扫参：`-ub` 512→1024 解码 **35.7 → 37.4 tok/s（+4.5%）**，pp 不变；
  已采纳到启动模板。2048 无额外收益。
- HIP/ROCm 后端（官方 b11212 win-rocm 构建）：需要另装 AMD HIP SDK 运行时
  （系统驱动不含 rocblas/amdhip64）。理论收益 ≤20%（解码是带宽瓶颈，
  当前 37 tok/s 已达理论带宽上限的 ~67%），未实测——装 SDK 后可用
  attic/rocm-build 对照验证。

## 3.7 HIP/ROCm 后端评估（官方 b11212 win-rocm 构建）

激活要点（本机已配好，产物在 attic/rocm-build 与 C:\LLM\llama-rocm）：
1. AMD HIP SDK 运行时（ROCm 6.4 已装，rocblas 就位）
2. ggml-hip.dll 找 `amdhip64.dll`，而 ROCm 6.4 只提供 `amdhip64_6.dll`
   → 复制改名放进 llama 二进制目录
3. HIP 运行时 bin 目录加入 PATH
4. llama.cpp `-dev ROCm0` 钉到独显（不钉会把模型劈给 iGPU gfx1036，
   走 PCIe 掉到 23 tok/s）

| 指标（27B IQ4_XS） | Vulkan | ROCm/HIP |
|---|---|---|
| pp512（小 KV） | 671 tok/s | **844 tok/s（+26%）** |
| pp8192 | 669 | 818（+22%） |
| tg128（小 KV） | 35.4 | 35.3（持平） |
| **96K KV 服务实测 decode** | **35.3** | 未测（预期持平或略低） |
| 160K KV（溢出态） | 19-22 | 22 |

**结论**：ROCm 预填充显著更快（长文档导入场景有价值），解码持平；
但两后端在大 KV 下都被溢出问题压制。当前定档 Vulkan + 96K；
若未来把上下文降到 32K 纯追速度或需要大文档预填充，可切 ROCm
（启动脚本需加 PATH 与 -dev ROCm0，见上文）。

## 4. 引擎与槽位管理实测

- 按需启动：热页缓存 10-25 秒 ready；真冷（WSL 重启后）1-4 分钟
- 闲置自停：整 300 秒准时停止（进程级），显存立即释放
- 互斥：A 槽占卡时 B 槽启动被拒，503 指名道姓；等 A 闲置自停后 B 可用
- 两个稠密 27B 全力档：14.3-14.6GB 权重 → 引擎运行时 18.1-18.7GB（160K KV）

## 5. 公网链路（Cloudflare Tunnel）

| 指标 | QUIC（默认） | http2（切换后） |
|---|---|---|
| 首请求 TTFB | 25.7s ❌ | 1.36s ✓ |
| 稳定态每请求开销 | 偶发抽风 | 稳定 0.6-1.5s |

大陆家宽到 CF 边缘 RTT ≈ 250-300ms 是物理下限；对 LLM 推理占比不大。
冷启动场景由 shim 的 SSE 心跳（15s 间隔注释行）保活，不会被边缘
100 秒空闲超时掐断。
